# Research Digest — Project Brief

**Date:** 2026-04-13
**Status:** Ready to build (clean rewrite)
**Source PRD:** `2026-04-13-research-digest-pipeline-prd-v2.md`

---

## 1. Problem

Researchers, clinicians, and domain professionals want to stay current with new academic papers in their field but don't want to run searches. Existing topic-based feeds (including the prior prototype of this system) either drown users in marginal papers or miss the specific angles they actually care about.

The prior prototype used OpenAlex topic-IDs plus prompt-time keyword extraction and proved too coarse. An 8-version iteration study across 4 reader profiles validated a better architecture — this project is the clean rewrite that embodies that finding.

## 2. Vision

A personal research assistant that delivers a ≤10-minute digest of new papers on a user-chosen schedule (daily, every other day, weekly, monthly, or custom). The user describes their interests once via a conversational onboarding agent, then receives — they never search. They refine the system by chatting with it, not by filling out forms.

## 3. Target users

- Academic researchers tracking a subfield
- Clinicians following evidence-based practice
- Industry R&D and product managers
- Non-academic professionals (marketers, educators, designers) who want research insights in their domain

## 4. Core approach

**Angles-first retrieval.** The user's stable interests are stored as 6–12 `core_angles`. Every scheduled run, a planner LLM generates fresh OpenAlex queries from those angles using current field vocabulary.

**Four-stage pipeline per run:**

1. **Planner** (LLM) — allocates a query budget across angles using field-knowledge reasoning, then writes tight-phrase + loose-synonym queries per angle slot.
2. **Retriever** (no LLM) — runs queries against OpenAlex, applies type filter, dedupes to a 200–500 paper candidate pool.
3. **Filter** (LLM, batched) — scores every candidate against the user's free-text profile as YES/PARTIAL/NO.
4. **Curator** (LLM) — generates digest HTML in the user's preferred style and sections.

Three LLM calls per run. Single model (`deepseek/deepseek-v3.2`) across all stages for v1.

**Onboarding is the highest-leverage quality investment.** A conversational agent elicits subject, profile, intent, schedule, and output style; proposes angles; and runs a corpus-sanity check against OpenAlex to catch angles too sparse for the user's chosen cadence. A bad angle list caps the entire pipeline's quality ceiling no matter how good the planner is.

**Configs are versioned and conversationally editable.** An update agent lets users refine their config in natural language; every change writes a new version row.

## 5. Technology stack

Next.js 16 + TypeScript 5 + Tailwind 4 frontend; Vercel AI SDK 6 + OpenRouter + DeepSeek v3.2 for all LLM calls; Supabase Postgres + Auth; Trigger.dev for scheduled jobs; Resend + React Email for delivery; OpenAlex as the paper source; Vitest for tests. Deploy to Vercel (Cloudflare Workers optional).

## 6. Data model (7 user-facing config fields)

`subject`, `schedule` (cron + IANA timezone + human description), `volume_target`, `profile` (free text — the filter's sole scoring context), `output_style` (free text — the curator's sole instruction), `core_angles` (the retrieval contract), `search_queries` (optional power-user escape hatch). Plus version metadata. Configs stored as JSONB; version history tracked in a separate table; every digest row references a specific config version.

## 7. Scope — v1

**In:** 4-stage pipeline, onboarding agent, preview digest, auth, dashboard, scheduler, email delivery, update agent, feedback loop, version history + rollback.

**Out:** Payments, tier enforcement, followed authors/institutions, citation graph features, mobile app, team accounts, multi-language digests.

## 8. Phases

1. **Pipeline** — standalone 4-stage pipeline + `/api/preview`, no DB. Must hit quality metrics before anything else.
2. **Onboarding agent + UI shell** — anonymous chat producing a config + preview digest.
3. **Persistence + auth** — Supabase setup, session→user linkage, dashboard, version history.
4. **Scheduler + delivery** — Trigger.dev schedules, Resend email, digest archive.
5. **Update agent + feedback loop** — conversational config editing, thumbs/promote feedback.
6. **Polish + production** — diagnostic mode, cost cap, rate limiting, observability.

## 9. Success metrics

**Pipeline quality** (must pass in Phase 1 before proceeding):
- ≥20 YES papers per digest on 3 of 4 test profiles
- ≥60% union precision on 3 of 4 profiles
- ≥1 YES paper on ≥70% of declared core_angles per run
- ≤$0.025 cost per digest run

**Product** (post-launch): onboarding→signup conversion, digest open rate, paper CTR, update-agent session rate, proposed-angle promotion rate.

**Reliability:** planner parse-error <3%, filter all-`?` <2%, Trigger.dev success >98%, email delivery >99%.

## 10. Cost model

~$0.015–0.020 per digest run. At 1000 users with a conservative weekly-dominant mix: ~$265/month (~$3.18/user/year). Even an all-daily worst case is ~$7.80/user/year — comfortable margin at any reasonable subscription price.

## 11. Key risks + mitigations

- **Bad angle lists** → showcase at onboarding silently retries, merges, and verifies each angle before `generateConfig`; spec at `docs/superpowers/specs/2026-04-14-onboarding-showcase-design.md`.
- **Filter scorer noise** (~25% drift measured) → single conversation across batches, retry on all-`?`, larger batch sizes.
- **Planner JSON parse errors** (~8% for DeepSeek) → up to 2 retries per call.
- **Phase 1 quality gate miss** → highest-risk phase intentionally front-loaded; pipeline must hit Section 12.1 metrics before any infrastructure is built.

## 12. Non-negotiables

- **Single source of truth:** the PRD. Do not import from the prior implementation.
- **Schedule is a first-class user choice**, elicited during onboarding and respected per-run.
- **Filter reads only `profile`; curator reads only `output_style`.** No cross-contamination.
- **Configs are never mutated in place** — every change creates a new version row.
- **Every `core_angle` gets ≥1 query** per run — no silent drops.
