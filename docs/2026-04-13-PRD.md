# Research Digest — PRD v2 (Clean Architecture)

## Context

Research Digest is a personalized paper-tracker. Users describe their research interests once via a conversational onboarding agent; the system then delivers a scheduled digest of new academic papers tailored to them. They never search — they receive.

This is a **clean rewrite** of an earlier prototype that used OpenAlex topic-IDs + keyword-string extraction at onboarding time. That approach was too coarse: topics drowned the user in marginal papers, and prompt-time keyword extraction couldn't adapt to the actual corpus state at each run's specific time window. A two-session iteration study (`iter/ITERATION_LOG.md`) tested 8 prompt versions across 4 reader profiles and found a clearly better architecture: **angles-first retrieval, with the planner generating fresh OpenAlex queries from angles every digest run**. v7.2 (model self-allocates query counts within an angle budget) + v7's per-angle slot discipline (tight phrase + loose synonym fallback) was the strongest combination.

This PRD specifies the system to build from scratch, embodying that finding. It carries over the technology choices from the prior project but discards the legacy schema and pipeline.

---

## 1. Product vision

Give every user a digest of new papers, **delivered on a schedule the user chooses** (daily, every other day, weekly, monthly, or any custom cadence/time/timezone), that:
- covers every angle they care about,
- filters out noise via an LLM scoring step over a real candidate pool (200-500 papers),
- reads in ≤10 minutes in their preferred style.

The system operates as a personal research assistant: onboarding conversation → living config → scheduled digests → ongoing refinement via chat. The user's relationship with the system is conversational, not configurational. **The schedule is a first-class user choice**, not a system default — the agent elicits it during onboarding and the runtime respects it for every run.

## 2. Target users

- Academic researchers tracking their subfield
- Clinicians following evidence-based practice
- Industry R&D + product managers tracking research relevant to their products
- Non-academic professionals (marketers, educators, designers) who want research insights in their domain

## 5. Data model

### 5.1 The config schema

The config is small and intentional. Free-text fields hold all the LLM-consumed intent; structured fields exist only where code needs them.

```typescript
import { z } from 'zod'

const angleSchema = z.object({
  id: z.number().int().min(1),
  text: z.string().min(1),
  status: z.enum(['core', 'proposed', 'rejected']).default('core'),
  priority: z.enum(['high', 'normal', 'low']).default('normal'),
})

export const digestConfigSchema = z.object({
  // === STRUCTURED — operational ===
  subject: z.string().min(1),
  schedule: z.object({
    // Cron expression is the canonical, fully-flexible storage format.
    // Supports: daily ('0 9 * * *'), weekly ('0 21 * * 1' = Mon 9pm),
    //          every other day ('0 9 */2 * *'), monthly ('0 9 1 * *'),
    //          every weekday ('0 9 * * 1-5'), any time/day combination.
    cron: z.string().min(1),               // standard 5-field cron
    timezone: z.string().min(1),           // IANA timezone, e.g. 'Europe/Istanbul'
    description: z.string().min(1),        // human-readable, generated by onboarding agent
                                           // e.g. "Every Monday at 9:00 PM"
                                           // Used for UI display only — runtime uses cron+timezone.
  }),
  volume_target: z.number().int().min(3).max(40),

  // === FREE TEXT — used by LLMs ===
  profile: z.string().min(1),             // who they are, what they want, anti-interests
                                          // — used by FILTER as scoring context
  output_style: z.string().min(1),        // tone, depth, sections, language
                                          // — used by CURATOR only

  // === STRUCTURED — retrieval contract ===
  core_angles: z.array(angleSchema).min(1),

  // === OPTIONAL — power-user escape hatch ===
  search_queries: z.array(z.string()).default([]),  // explicit must-run queries

  // === METADATA ===
  version: z.number().int().min(1),
  created_at: z.string(),  // ISO timestamp
  updated_at: z.string(),
})

export type DigestConfig = z.infer<typeof digestConfigSchema>
```

**7 user-facing fields**, plus metadata. Compare to ~20 fields in the legacy schema.

### 5.2 Why the schema is shaped this way

Key decisions, all grounded in the iter study findings:

1. **`profile` is one big free-text blob** because the FILTER step is the heaviest LLM consumer of profile context (~300 paper-scoring calls per digest), and splitting it across fields creates coordination problems. Anti-interests, inclusion criteria, scoring preferences all live in the profile prose. The onboarding agent writes it; the filter reads it; nothing else.
2. **`output_style` is separate from `profile`** because it has a different consumer (the curator) and including formatting instructions in the filter's context is wasted noise. The curator reads `output_style` once per digest run.
3. **`core_angles` is the retrieval contract.** Every angle is guaranteed at least one query per run. Angles capture the user's stable interests; queries (generated per run by the planner) capture the field's current vocabulary state.
4. **No `core_topics` (OpenAlex topic IDs).** The legacy approach of mapping interests to coarse OpenAlex topics drowned digests in marginal papers. Angles + planner-generated keyword queries do better at both precision AND recall. The planner uses its field knowledge to allocate query budget — that's where the intelligence lives, not in pre-stored topic IDs.
5. **No `followed_authors`, `followed_institutions`, `landmark_papers`, `adjacent_interests`, `inclusion_criteria`, `exclusion_criteria`, `preferred_journals` as structured fields.** Anti-interests and inclusion criteria embed naturally in `profile`. The other fields can be added in v2 if real users actually want author tracking — for v1, dropping them eliminates schema noise.
6. **`search_queries` is optional.** Power users who want explicit must-run queries can have them; default users never see this field.

## 6. Pipeline stages

### 6.1 Planner (the core of the system)

**Purpose**: Given a config, produce a query plan that (a) guarantees every core_angle gets queries allocated by field richness, (b) uses slot-discipline within each angle for precision, (c) optionally proposes 1-2 new dynamic angles per run.

**Empirical basis**: from the iter study (`iter/ITERATION_LOG.md`), 8 prompt versions tested across 4 profiles (LLM agents, marketing, AFib, adolescent depression) with stable cross-version scoring:

| Version | Strategy | YES/run | Precision |
|---|---|---|---|
| v0 | Free-form, no angle contract | 21 | 55% |
| v7 | Fixed 2 queries per angle | 27 | 55% |
| **v7.2** | **Model self-allocates within budget** | **27** | **53%** |
| v8 | v7 + diagnostic + backfill | 28 | 55% |

v7.2 was the first version with no profile-specific regressions. v8's diagnostic adds value as reporting; its backfill mechanism doesn't earn its 2.5× cost. The shipping planner is **v7.3**: v7.2's allocation block + v7's slot-discipline language merged. Each component was validated; the merge is the natural next step.

#### 6.1.1 Inputs

```
SUBJECT: <config.subject>

PROFILE:
<config.profile>      # free text — role, intent, anti-interests all embedded

REQUIRED_ANGLES (you MUST cover every one):
  1. <angle text>
  2. <angle text>
  ...
  K. <angle text>

QUERY_BUDGET: <int>   # default 16 for ≤8 angles, 24 for ≤12, scale linearly
MIN_PER_ANGLE: 1
MAX_PER_ANGLE: 4
DYNAMIC_MODE: <bool>  # default false; enable post-MVP
TIME_WINDOW_DAYS: <int>  # derived from the schedule cadence — see 6.2.4 below.
                         # Daily=1, every-other-day=2, weekly=7, biweekly=14, monthly=~30.
                         # Informational only — planner does NOT put dates in queries.
```

#### 6.1.2 Output schema

```typescript
const queryPlanSchema = z.object({
  subject: z.string(),
  allocation: z.array(z.object({
    angle_id: z.number().int().min(1),

    reason: z.string(),
  })),
  queries: z.array(z.object({
    id: z.number().int().min(1),
    angle_id: z.number().int().min(1),
    slot: z.number().int().min(1),
    query: z.string().min(1),
    rationale: z.string(),
  })),
  proposed_angles: z.array(z.object({
    text: z.string(),
    reason: z.string(),
    queries: z.array(z.object({
      slot: z.number(),
      query: z.string(),
      rationale: z.string(),
    })),
  })).default([]),
  coverage_notes: z.string(),

```

#### 6.1.3 Prompt requirements

The planner system prompt MUST enforce the following:

1. **Two-step output**: the `allocation` block MUST appear before `queries` in the JSON. Each allocation entry has angle_id, queries (count), and a one-line `reason` invoking field knowledge.

2. **Allocate by field knowledge**: instruct the model explicitly:
   > "Allocate more queries to angles where the field publishes prolifically AND the canonical phrasing generalizes cleanly. Allocate fewer (minimum 1) to angles that are niche, settled (e.g., a debate closed by a specific landmark trial), or hard to phrase precisely. Use your background knowledge of which sub-fields are active vs dormant. Output a one-line reason per angle that names the specific reasoning."

   In testing, this produced reasoning like *"settled debate with EAST-AFNET 4, few truly new comparison studies → 1 query"* — the model literally cited the trial that closed the rate-vs-rhythm-control question. This is the win that v7.2 unlocked.

3. **Slot discipline per angle**:
   - **Slot 1** = tight phrase anchor: most specific quoted phrase that names this angle, AND-ed against the subject. `"interpersonal psychotherapy" AND ("adolescent" OR "teen") AND depression`.
   - **Slot 2** = loose synonym fallback: broader OR group of terminological variants. `("IPT-A" OR "interpersonal therapy" OR IPT) AND ("adolescent depression" OR "teen depression")`.
   - **Slot 3+** (only for richly-allocated angles, count ≥ 3) = sub-axes: named methods, instruments, sub-techniques. NEVER drift to a different angle.

4. **Dynamic angle proposals** (only when `DYNAMIC_MODE=true`): model may propose 0-2 new angles with a one-line justification each. These get flagged for user review in the digest sidebar; not promoted to core without explicit user feedback.

5. **Hard query rules** (validated as winning in the test harness):
   - Every core_angle gets ≥1 query — no silent drops.
   - At most 2 AND-separated concept clusters per query. Triple-AND queries average 3-5× lower recall.
   - All OR groups parenthesized. `A OR B AND C` parses as `A OR (B AND C)`, which floats `A` unscoped.
   - No date predicates inside queries (the retrieval layer handles dates).
   - No methodology phrases (`"randomized trial"`, `"meta-analysis"`, `"systematic review"`) as the sole specificity carrier — they match every field.
   - Every query scoped to the subject. Generic terms like `"agent"` get an AND clause like `AND ("LLM" OR "language model")`.

6. **Reference prompts to merge**: the v7.2 base lives at `iter/prompts/v7_2_self_allocate.md`. The slot-discipline language to merge in lives at `iter/prompts/v7_slotfilled.md`. Use both as the source-of-truth for prompt content.

#### 6.1.4 Budget enforcement

- **Soft cap**: allow up to `query_budget * 1.25` queries total. The model may judge that a profile with many angles needs more capacity than the hint. Log overflow but don't reject.
- **Hard cap**: if total > `query_budget * 1.5`, retry the planner once with an explicit budget reminder. If it overflows again, accept and log.
- Each angle's `queries` count must satisfy `min_per_angle ≤ count ≤ max_per_angle`.
- Every angle in REQUIRED_ANGLES must appear in `allocation` (validate before accepting the response).

#### 6.1.5 Model + params

- Model: `deepseek/deepseek-v3.2`
- Temperature: **0.7**. The plan-structure analysis in `iter/analyze_plan_diversity.py` showed temperature 0.3 doesn't reduce variance meaningfully but does produce more synonym-bundled (less precise) queries.
- Parse-error retry: up to 2 attempts on JSON parse failure (~8% rate measured for DeepSeek)
- Single LLM call per digest run (no two-pass diagnostic by default)
- Cost: ~$0.002/run

### 6.2 Retriever

**Purpose**: Execute every planner query (plus any user-defined `search_queries`) against OpenAlex, dedupe across all sources, produce a candidate pool of 200-500 unique papers.

**No LLM. Pure orchestration over the OpenAlex client.**

#### 6.2.1 Implementation requirements

1. **OpenAlex client** with the following methods (port from existing or write fresh — code is straightforward):
   - `searchByKeyword(query, fromDate, toDate, perPage, page) → Work[]`
   - `searchByAuthor(authorId, fromDate, toDate)` — for v2 (when `followed_authors` is added)
   - `reconstructAbstract(invertedIndex) → string` — OpenAlex returns abstracts as inverted indices
   - `workToCandidatePaper(work, source) → CandidatePaper`

2. **OpenAlex query construction** (CRITICAL — these were validated in the iter study):
   - `search=` parameter takes the raw query string
   - `filter=from_publication_date:YYYY-MM-DD,to_publication_date:YYYY-MM-DD,type:article|review|book-chapter|preprint|dissertation|report|peer-review`
   - **The type filter is mandatory.** It excludes datasets, libguides, product listings, coupon pages — content that lifts precision **+15pp** when filtered out.
   - `per_page=50`, paginate up to 4 pages per query (max 200 hits per query)
   - `select=id,doi,title,publication_date,authorships,primary_location,abstract_inverted_index,cited_by_count,is_oa,oa_url,topics,keywords`
   - Always include `api_key` and `mailto` for the polite pool (10 req/sec)

3. **Concurrency**: cap simultaneous OpenAlex requests at 5-8 using a semaphore (e.g., `p-limit`). The iter study saw 429 errors with naive parallel runs.

4. **Dedup**: by DOI first, then by normalized title prefix (lowercased, first 120 chars). OpenAlex sometimes returns preprint + published versions of the same work.

5. **Source tagging**: every candidate carries a `sources: string[]` array — `['angle:4/slot:1']` or `['angle:4/slot:1', 'search_query:CBT-A']` if the same paper came from multiple queries. Used by the filter for per-angle attribution.

#### 6.2.2 Output contract

```typescript
interface CandidatePaper {
  id: string                       // OpenAlex ID, e.g. "W4392056789"
  doi: string | null
  title: string
  authors: string                  // pre-formatted "Smith J, Lee K, Tanaka R"
  journal: string | null
  date: string                     // 'YYYY-MM-DD'
  abstract: string | null          // reconstructed from inverted index
  topic: string | null             // OpenAlex primary topic name (display only)
  cited_by_count: number
  is_oa: boolean
  oa_url: string | null
  keywords: string[]
  primary_topic_score: number | null
  sources: string[]                // ['angle:4/slot:1', ...]
}
```

#### 6.2.3 Target pool size

- **200-500 unique candidates** per typical weekly-cadence run. Smaller cadences (daily) naturally produce smaller pools; larger cadences (monthly) produce larger pools. The filter handles the size variance gracefully.
- If the pool comes in **under (volume_target × 4)**, log a warning to `run_output` for debugging — likely indicates queries are too narrow OR the time window has unusually low publication volume for this period.
- For very short cadences (daily), expect 30-80 candidate papers per run — that's normal, not a bug. The filter's job is the same regardless of pool size.

#### 6.2.4 Time window derivation from schedule

The retriever computes `from_publication_date` and `to_publication_date` for each run from the user's cron schedule, NOT from a hardcoded "7 days ago" rule:

```
to_date   = the current scheduled fire timestamp (the moment this run started)
from_date = the previous fire timestamp computed from the cron expression in the
            user's timezone (the previous time this same schedule would have fired)
```

Examples:
- Daily cron `0 9 * * *`: from = yesterday 9am, to = today 9am → 1-day window
- Weekly cron `0 21 * * 1`: from = previous Monday 9pm, to = this Monday 9pm → 7-day window
- Every other day `0 9 */2 * *`: from = 2 days ago 9am, to = today 9am → 2-day window
- Monthly cron `0 9 1 * *`: from = first of last month, to = first of this month → ~30-day window

Use a cron-parsing library (e.g., `cronstrue` for descriptions, `cron-parser` for prev/next computation) to derive these timestamps. Always compute in the config's `timezone`, not server local time, so the user's "9am Monday" is their 9am, not UTC.

For the very first run after activation, there is no previous fire — use a fallback window equal to the cron's natural cadence (e.g., 7 days for a weekly schedule, 1 day for daily).

Pass the resulting `from_date` and `to_date` to OpenAlex via the `from_publication_date` / `to_publication_date` filters. The planner receives `TIME_WINDOW_DAYS = (to_date - from_date).days` as an informational input only — it does not embed dates into queries.

### 6.3 Filter

**Purpose**: Score every candidate paper in the pool against the profile and select the top N for the digest.

#### 6.3.1 Approach

- **Batch the scoring**: feed candidates in batches of 40-60 to the LLM (title + 1-2 line abstract snippet + source tag). Multiple batches if pool > 60. ALL batches use the same system prompt + profile so labels are consistent.
- **Single context source**: the scoring prompt receives `config.profile` (the free-text blob) only. Do NOT inject `config.output_style` — that's for the curator.
- **Three-bucket categorical labels**: `YES` (clearly relevant), `PARTIAL` (tangentially related), `NO` (off-topic). The categorical scheme was validated in the iter study; do not change to numeric scores or letter grades.

#### 6.3.2 Prompt structure

Reference `score_titles()` in `iter/score_plan.py`:

```
You are a paper relevance classifier. Given a reader profile and a list of paper titles, classify each title as one of:

- YES — clearly relevant to what the reader wants
- PARTIAL — tangentially related (same broad area but wrong specialty or angle)
- NO — off-topic (different field, or area the reader explicitly doesn't want)

Respond with ONLY a JSON object:
{"scores": [{"i": 1, "label": "YES", "why": "one-sentence reason"}, ...]}

No prose. No explanation outside the JSON.
```

Extend this with the user prompt containing `READER PROFILE: <config.profile>` and the numbered candidate list.

The `why` field is new vs the test harness — the curator uses it as the per-paper "this matters to you because…" line. Keep it to one short sentence.

#### 6.3.3 Output → digest selection

After all batches return:

1. Compute per-angle YES counts (uses each candidate's `sources` array for attribution)
2. Take the top `config.volume_target` papers, prioritizing YES over PARTIAL, with optional weighting by `cited_by_count` for ties
3. If fewer YES papers than `volume_target`, fill with the highest-relevance PARTIAL papers
4. Persist the full per-paper score map in `run_output.filter.scores`
5. Persist the per-angle coverage in `run_output.filter.angle_coverage`

#### 6.3.4 Model + params

- Model: `deepseek/deepseek-v3.2`
- Temperature: **0.0** (despite ~25% drift between calls observed in tests, 0.0 is the right setting for classification; see scorer-noise note below)
- Cost: ~$0.008/run for a 300-paper pool

#### 6.3.5 Scorer noise mitigation

The iter study measured ~25% YES/PARTIAL drift between scorer calls at temp=0.0. Mitigations:

1. **Single conversation, multiple batches**: all batches within one digest run share the same system prompt (already the case if you batch correctly). Don't restart conversations between batches.
2. **Retry on all-`?` output**: ~1 in 5 DeepSeek scoring calls in the test harness returned empty labels. Detect this (`label == '?'` for all entries) and retry once.
3. **Per-batch consistency**: the model's labeling drifts across runs but is mostly consistent within a single batch call. Larger batches (50-60) are more stable than many small batches.

### 6.4 Curator

**Purpose**: Take the top-N filtered papers and generate the digest HTML in the user's preferred style.

#### 6.4.1 Inputs

- `config.subject`
- `config.profile` (for the "this matters to you" framing — optional, the curator can rely mostly on `output_style`)
- `config.output_style` (the primary instruction — sections, tone, depth, language)
- The selected papers, each with: title, authors, journal, date, DOI, abstract (snippet), citation count, OA status, **and `why_relevant`** (the one-sentence reason from the filter)
- Any `proposed_angles` from the planner (rendered in a separate "we also found these" section if present)

#### 6.4.2 Output

- A self-contained HTML fragment (no `<html>` / `<body>` tags)
- Inline CSS (works in email clients; React Email wraps it for delivery)
- Clean, modern, semantic structure — h2 headings per section, paper blocks, paragraph summaries
- Each paper has a `data-paper-id` attribute on its container element so click-tracking can attribute clicks to OpenAlex IDs
- If `proposed_angles` are present, append a final section: "We also found these — was this useful?" with thumbs-up/down buttons that POST to `/api/feedback`

#### 6.4.3 Prompt structure

```
You are generating a research digest for one reader.

READER PROFILE:
<config.profile>

OUTPUT STYLE:
<config.output_style>

PAPERS SELECTED FOR THIS DIGEST:
<numbered list of papers, each with title, authors, abstract, date, DOI, citation count, OA status, why_relevant>

Generate the digest as a self-contained HTML fragment (no <html>/<body> tags). Use clean, modern styling with inline CSS. Follow the OUTPUT STYLE for sections and tone. For each paper, weave the `why_relevant` line naturally into the summary — don't quote it verbatim. Include each paper's title with a link to its DOI (or OpenAlex page if no DOI). Add data-paper-id="<openalex_id>" to each paper's container element for click tracking.

If PROPOSED_ANGLES are present, append a final section titled "We also found these — was this useful?" listing each proposed angle with its papers and thumbs-up/down buttons (use <button data-feedback="thumbs_up" data-angle-id="...">).
```

#### 6.4.4 Model + params

- Model: `deepseek/deepseek-v3.2`
- Temperature: 0.5 (tested as a reasonable middle ground for HTML generation; not benchmarked against alternatives — the curator step was not iterated in the test harness)
- Cost: ~$0.005/run

If HTML quality is insufficient at v1 launch, the curator is the most likely stage to swap models on first (Kimi K2.5 has anecdotally produced cleaner HTML in the prior project).

### 6.5 Diagnostic (optional)

**Purpose**: Classify each core_angle as `covered` / `marginal` / `wrong_corpus` / `empty_corpus` for honest reporting in the digest UI.

**When**: only when `DIAGNOSTIC_MODE=true` (env var or per-config setting). Default: off.

**Critical**: **No backfill queries.** The iter study's v8 test showed the diagnostic itself is valuable as reporting ("no IPT-A papers found this week" is honest and useful), but its backfill recovery loop costs 2.5× and doesn't help for empty-corpus angles by definition.

**Input**: the per-angle filter results (queries run, hit counts, top-5 titles with labels).

**Output**: structured `angle_diagnoses` array, persisted in `run_output.diagnostics`.

**Cost**: ~$0.002/run.

## 7. Onboarding agent

### 7.1 Purpose

Through a conversational chat, produce a complete `digest_config` v1 that the planner can use immediately. The output is a `DigestConfig` JSON validated against the schema in 5.1.

### 7.2 The conversation

Information goals (achievable in any order, skipping what's already been said):

1. **Their role + context** — researcher, clinician, developer, marketer, hobbyist? Shapes everything.
2. **The subject** — what's the main topic they want a digest about?
3. **Their intent** — what they want to DO with the research (track a field, find practical tips, stay current for clinical practice, apply findings to work, etc.). The single biggest driver of digest format.
4. **Anti-interests** — what they don't want (no animal studies, no basic-science, no preprints, etc.). Captured into the profile prose, not as separate fields.
5. **Style preferences** — depth, technicality, tone. Often inferred rather than asked.
6. **Schedule** — how often and when they want the digest. Always ask explicitly (don't default silently). Accept anything the user says: "every Monday at 9am", "every other day in the morning", "twice a week", "daily at 7am", "first of every month". The agent normalizes this to a cron expression + IANA timezone + a human description (see 7.6 for the conversion). The agent should validate the user's timezone — if it doesn't know it, ask: "What city are you in? I'll figure out the timezone from that." A schedule is required to finalize the config.

#### Conversational discipline (carry over from successful prior prompt):

- One question per message. Never two.
- 2-3 sentences per message. Never long paragraphs.
- Give before you ask: every reply after the first should reflect/infer something that proves you understood, then ask the next question.
- Suggest before they ask: when you can infer something (sections, depth, adjacent sub-areas), propose it. Don't wait to be asked.
- No system jargon: never say "config", "OpenAlex", "queries", "topics", "schema". Talk about "your digest", "what I'll track for you", "papers I'll look for".
- Don't ask about things you can infer: a marketing director who wants consumer psychology research already gets accessible tone + practical takeaways inferred — don't ask to confirm.
- Aim for a finalizable config in **4-6 exchanges**. Hard wrap at ~10.

### 7.3 The angle proposal step (the new core)

Once the agent understands subject + role + intent, it calls a `proposeAngles` tool that runs an internal LLM call returning 6-12 candidate angles for this subject + profile combination. The agent then presents them naturally:

> "Based on what you've told me, here are the specific areas I'll track for you within atrial fibrillation:
>
> - Catheter ablation techniques and outcomes
> - Anticoagulation choices (DOAC selection, bleeding risk)
> - Rate vs rhythm control strategies
> - Stroke prevention and LAAC devices
> - New clinical trials and guideline updates
> - Wearable/remote monitoring
>
> Want to add or remove any of these?"

The user refines verbally. The agent updates the angle list and may iterate once more if needed.

#### `proposeAngles` tool spec

Internal LLM call (DeepSeek v3.2). Input: subject + profile-summary-so-far. Output: 6-12 angles with optional priorities. The internal call uses the same field-knowledge instinct that the planner uses for allocation: prefer angles that are productive sub-areas with clear vocabulary; avoid angles that are too generic ("randomized trials") or too narrow to have weekly volume.

### 7.4 Corpus-sanity check (the second new step)

After angles are finalized AND the user has chosen a schedule, for the 2-3 angles the agent is least confident about, it silently runs a test OpenAlex query (basically a single planner-style query for that angle) and checks the hit count over the past **30 days** as a baseline measurement.

The threshold scales with the user's chosen cadence: convert the 30-day count to **expected papers per cadence window**:

```
papers_per_run = (count_30_days / 30) * cadence_days
```

where `cadence_days` is derived from the schedule (1 for daily, 2 for every-other-day, 7 for weekly, 30 for monthly, etc.).

If `papers_per_run < 2` for a given angle, the agent should:
- **Merge** it with a broader sibling angle, OR
- **Flag** it to the user with cadence-aware language: *"Heads up — based on your <daily | weekly | monthly> schedule, '<angle>' will likely be empty in most digests because there are only ~<X> papers per <cadence> on this topic. Keep it anyway?"*, OR
- **Drop** it if the user confirms they don't need it specifically

This step is the most important quality investment in the entire system. The strongest finding from the iter study: **a good planner cannot save a bad angle list**. Half the "planner failures" we observed were really angle-list problems — angles too narrow to have papers any given run, or too generic so every query drifts to adjacent topics. Catching these at onboarding prevents users from receiving consistently empty sections.

**Cadence note**: a daily user with very narrow angles will hit empty-corpus issues much faster than a monthly user with the same angles. The agent should mention this trade-off when a user picks a daily cadence with niche interests: *"With a daily schedule, your digest may sometimes have only 1-2 papers because the field doesn't publish that fast. Want a weekly schedule instead?"*

### 7.5 Style + sections

After angles are confirmed, the agent proposes sections + style based on role + intent. Examples:

- **Developer tracking AI research**: "Latest Highlights" (3-4 plain-language findings) + "What You Can Use" (practical applications) + sources list at the bottom
- **Clinical psychologist**: "Quick Summary" + "Evidence Updates" (clinical implications per paper) + "Watch List" (emerging trends)
- **Marketing professional**: "30-Second Brief" + "Key Findings" (accessible summaries) + "Apply This Monday" (concrete suggestions)
- **Academic researcher**: "Overview" + "Paper Details" (objective/methods/results/limitations/relevance) + "Citation Watch"

The agent presents these sections in the chat and asks for confirmation. The final `output_style` is a free-text blob that captures the section design, tone, depth, and any specific instructions.

### 7.6 Schedule normalization (cron conversion)

The user describes their schedule in natural language. The onboarding agent must convert it to a `{cron, timezone, description}` triple before calling `generateConfig`. Examples:

| User says | cron | timezone | description |
|---|---|---|---|
| "every Monday at 9am, I'm in Istanbul" | `0 9 * * 1` | `Europe/Istanbul` | "Every Monday at 9:00 AM" |
| "daily at 7am" | `0 7 * * *` | (ask for city) | "Every day at 7:00 AM" |
| "every other day in the morning" | `0 8 */2 * *` | (from user) | "Every 2 days at 8:00 AM" |
| "first of every month" | `0 9 1 * *` | (from user) | "1st of every month at 9:00 AM" |
| "weekdays at 8am" | `0 8 * * 1-5` | (from user) | "Weekdays at 8:00 AM" |
| "twice a week, Mon and Thu" | `0 9 * * 1,4` | (from user) | "Every Monday and Thursday at 9:00 AM" |

The agent should:
1. Parse the user's intent (frequency + day-of-week + time-of-day if specified)
2. Default the time to 9:00 AM if the user doesn't specify
3. Ask for the timezone if it's not already known from the conversation
4. Generate the cron expression
5. **Confirm the schedule back to the user in natural language** before calling `generateConfig`: *"Got it — I'll send your AFib digest every Monday at 9:00 AM Istanbul time. Sound good?"*

For irregular cadences cron can't represent cleanly (e.g., "every 3 days starting from today"), the agent should propose the closest cron approximation and explain the trade-off (e.g., `0 9 */3 * *` resets at month boundaries — the agent should either accept this minor drift or suggest a regular weekly cadence).

A `validateCron(cron, timezone)` tool can help: it parses the cron string, computes the next 3 fire times, and returns them so the agent can show the user *"Your next three digests will arrive on: Mon Apr 14, Mon Apr 21, Mon Apr 28."*

### 7.7 Output: `generateConfig` tool

Once everything is settled, the agent calls `generateConfig(...)` with the full DigestConfig. The tool validates against the Zod schema and returns it to the user for a final preview.

### 7.8 Sign-up linkage

The chat is anonymous — config is stored under a `session_id` cookie. On sign-up, the config is linked to `user_id`, the `digest_configs` row is created, and the first `digest_config_versions` row is inserted with `version=1, changed_by='onboarding'`.

### 7.9 Model + params

- Model: `deepseek/deepseek-v3.2`
- Temperature: 0.7 (conversational)
- Streaming via Vercel AI SDK
- Cost per onboarding: ~$0.03 (10-20 messages including tool calls)

## 8. Update agent

### 8.1 Purpose

A conversational channel for users to refine their config over time without filling out forms. The user says "add pulsed-field ablation" or "I'm getting too many CBT papers, focus more on family therapy" and the agent edits the config in natural language.

### 8.2 When invoked

- **User-initiated** (primary): "Chat with your research assistant" button in the dashboard
- **System-prompted**: after 4 weeks of digests, after significant click-pattern shifts, every 3 months as a check-in

### 8.3 Context the agent receives

- The current config (full DigestConfig)
- Last 3-5 config versions (history of what changed)
- Last 4 weeks of digest summaries (papers per angle, click signals)
- Click/feedback signals from `digest_feedback`

This lets the agent open with informed observations: *"I noticed you've been skipping the genetics papers — want me to deprioritize that angle?"* instead of a blank slate.

### 8.4 Tools

- `updateConfig(patch)` — structured patch to the current config (add/remove/edit `core_angles`, edit `profile`, edit `output_style`, etc.)
- `commitVersion(changelog)` — finalizes the update, writes a new `digest_config_versions` row, increments `digest_configs.version`

### 8.5 Quality gate

The agent MUST confirm before committing:

> "OK — I'll add 'pulsed-field ablation' as a new angle and drop 'rate vs rhythm control' since you mentioned that's settled for you. Commit these changes?"

User confirms → `commitVersion` is called with a one-line changelog.

### 8.6 Rollback

The dashboard shows version history with changelogs. Selecting a prior version copies it back into the current config and bumps the version number with changelog `"rolled back to v3"`.

### 8.7 Model + params

- Model: `deepseek/deepseek-v3.2`
- Temperature: 0.7
- Cost per session: ~$0.02

## 9. Scheduler + delivery

### 9.1 Trigger.dev

- Config save → take `config.schedule.cron` and `config.schedule.timezone` → create/update Trigger.dev schedule with that cron + timezone → store `trigger_schedule_id` in the `digest_configs` row.
- On schedule fire → Trigger.dev task runs the digest pipeline (planner → retriever → filter → curator) for the given config. The task receives the actual fire timestamp (`to_date`) and computes `from_date` from the cron's previous fire time in the user's timezone (see 6.2.4).
- On completion → save digest row, call Resend to send email.

**Dependencies needed**: `cron-parser` for computing previous/next fire times, `cronstrue` (optional) for human-readable descriptions if the agent hasn't already produced one.

### 9.2 Files (create)

- `src/trigger/digest-job.ts` — Trigger.dev task definition
- `src/lib/trigger/client.ts` — wrapper for creating/updating schedules
- `src/app/api/configs/[id]/activate/route.ts` — marks config as active, creates Trigger schedule
- `src/app/api/configs/[id]/pause/route.ts` — pauses schedule

### 9.3 Retry + error handling

- Planner parse-error retry (up to 2 attempts)
- Filter all-`?` retry on empty scoring (up to 2 attempts)
- OpenAlex 429 → exponential backoff, max 3 retries
- Total pipeline failure → save digest row with `status='failed'`, expose in dashboard, optionally email user

### 9.4 Cost cap per run

Hard cap on LLM cost per digest run (configurable, default $0.05). If exceeded, abort and log. Protects against runaway loops.

### 9.5 Email delivery

- Install `resend` + `@react-email/components`
- `src/emails/digest-email.tsx` — React Email template wrapping the curator's HTML
- Trigger.dev task calls Resend after digest HTML is generated
- Store `delivered_at` on the digest row
- Unsubscribe link in footer

| Stage | Tokens (in/out) | Cost |
|---|---|---|
| Planner | ~1.5K / ~2K | $0.002 |
| Retriever (OpenAlex API) | — | free (~$0.008 over OpenAlex free tier) |
| Filter (~300 papers) | ~20K / ~2K | $0.008 |
| Curator | ~5K / ~3K | $0.005 |
| Diagnostic (optional) | ~5K / ~1K | $0.002 |
| **Total / digest** | | **$0.015-0.020** |

**Onboarding** (one-time per user): ~$0.03
**Update agent session**: ~$0.02

### 13.1 Cost scenarios by cadence mix

For 1000 users, costs scale with **runs per user per month** — daily users cost ~7× a weekly user, monthly users ~¼×. Plan for a mix.

**Conservative scenario** (mostly weekly users):
- 800 weekly + 100 daily + 50 biweekly + 50 monthly = ~6,750 runs/month
- LLM costs: ~$135/month
- OpenAlex over free tier: ~$60/month
- Resend: $20/month
- Supabase/Trigger.dev/hosting: ~$50/month
- **Total: ~$265/month** at 1000 users = **~$3.18/user/year**

**Pure weekly baseline** (the simplest scenario): ~4000 runs/month, ~$190/month total, ~$2.28/user/year.

**All-daily scenario** (worst-case): 30,000 runs/month, ~$650/month, ~$7.80/user/year.

Even the all-daily scenario leaves comfortable margin at any reasonable subscription price ($5-15/month). Cadence is a meaningful cost lever — when users pick daily, they're costing the system 4-7× more per month than weekly users. Worth surfacing in the dashboard analytics for capacity planning, not in user-facing UI.
